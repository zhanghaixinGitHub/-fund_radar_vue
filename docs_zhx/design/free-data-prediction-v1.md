# 基金雷达：免费已授权数据预测 V1 设计

> 关联需求：[当前 2000 积分可用数据补齐](../requirements/tushare-2000-data-completion.md)、[自选与预测模块](../requirements/watchlist-prediction-module.md)
> 版本：v1.1 ｜ 日期：2026-09-02 ｜ 变更等级：L3 ｜ 状态：V1.0 最小范围已确认；待按阶段实施

## 1. 结论和目标

在不购买基金股票持仓、新闻、公告等付费数据的前提下，先做一个以“基金自身历史净值 + 当时已披露的公共基金信息 + 市场状态”为输入的日频方向概率模型。它回答的是：

> 截至某个明确数据日，未来第 20 个交易日，该基金净值上涨的历史条件概率是多少？

它不是买卖建议，不承诺预测一定正确，也不声称知道基金现在持有哪些股票。模型首先要通过严格的历史滚动回测；回测不达标就只展示数据状态，不发布概率。

## 2. 产品范围

### 2.1 第一阶段支持对象

| 分类 | V1 处理方式 | 原因 |
| --- | --- | --- |
| 股票型基金 | 首批支持，目标为未来 20 个交易日方向 | 历史净值较充足，市场状态的解释价值相对更高 |
| 混合型基金 | 与股票型分开建模，达到样本与回测门槛后再启用 | 风险暴露差异较大，不能直接共用股票型模型 |
| 债券型、货币型、其他 | V1 不发布方向概率 | 收益机制与数据特征不同，混在一起会制造错误精度 |
| ETF/LOF | 仅在基础档案和日线完整时作为独立子类评估 | 场内价格与场外净值不能混作同一个标签 |

当前数据快照中有 24 只股票型、15 只混合型、2 只债券型和 2 只其他基金。V1 先以股票型做可用基线；这是减少异质性，不是对其他基金下结论。

### 2.2 不纳入 V1 的内容

1. 基金的股票持仓、行业真实暴露和重仓股涨跌：当前没有 `fund_portfolio` 授权，禁止猜测；
2. 新闻、公告、研报和社交情绪：当前不购买相应权限，也不以未经授权的抓取替代；
3. 用户个人买入金额、成本、盈亏和风险偏好：公共预测与个人投顾分离；
4. 分钟级、实时价格和盘中交易提示：V1 只用有明确截至日的日频数据；
5. “必涨”“稳赚”“建议买入/卖出”等交易结论。

## 3. 数据输入与时间边界

本设计依赖 [数据补齐需求](../requirements/tushare-2000-data-completion.md) 的 P0 数据。每一条特征都必须同时记录 `as_of_date`（预测截点）和 `available_at`（当时实际可获得日期）。回测时，`available_at > as_of_date` 的记录一律不可用。

| 特征组 | 主要数据 | 举例 | 使用原则 |
| --- | --- | --- | --- |
| 基金自身走势 | 单位净值、累计净值、复权口径 | 5/10/20/60 日收益、波动率、最大回撤、均线距离、历史分位 | 只计算截至预测日已经确认的净值；分红导致的机械跳变要处理 |
| 基金自身风险状态 | 净值历史 | 下行波动、连续回撤天数、收益偏度、相对自身历史位置 | 不使用未来区间的最高/最低值 |
| 基金经理 | 历史任职记录 | 截点任职天数、近 90 日是否换经理、多经理标识 | 任职年限以当时截点计算，不能把今日经理带回过去 |
| 基金规模和份额 | 历史份额快照 | 份额同比/环比、规模分层、最近披露距今天数 | 低频且可能缺失；缺失本身作为特征并保留质量标识 |
| 分红事件 | 历史分红/除权日期 | 最近分红距今天数、除权窗口标识 | 只用于避免把规则性净值变化误读为市场波动 |
| 基金档案 | 基金类型、成立日、费率等 | 基金年龄、类型、场内/场外标识 | 类型用于分模型，不能用来替代持仓风格 |
| 市场状态 | 已授权指数目录、分类、日线、权重 | 宽基指数 5/20 日收益、市场波动、成长/价值或行业指数状态 | 是“外部天气”，不是拿另一只基金来比输赢；指数无法识别时可降级 |

### 关于“可用基准”的更正与定义

基金自身净值历史足以构造一个“自身方向基线模型”，因此没有市场指数时，仍可以回测并输出标明范围的自身走势概率。此前“没有基准就不能做预测”的说法过强，本设计不再采用。

这里的市场参考指数有两个可选作用：

1. 作为模型输入，区分“整个市场普遍上涨”与“基金相对自身节奏的变化”；
2. 作为解释文字，让用户知道当期市场环境，而不是把某只别的基金强行作为比较对象。

它不是发布 V1 的硬性前置条件。若指数数据缺失，系统可运行 `OWN_NAV_DIRECTION_BASELINE`，同时明确标记“未启用市场状态特征”；若指数数据完整且滚动回测证明有稳定增益，才升级为 `OWN_NAV_PLUS_MARKET_V1`。

## 4. 标签、模型和输出

### 4.1 预测标签

对基金 `f` 在预测截点 `t`，计算未来第 20 个有效交易日的累计净值变化：

```text
future_return_20d = adjusted_nav(f, t + 20) / adjusted_nav(f, t) - 1
label_up_20d = 1,  当 future_return_20d > 0
label_up_20d = 0,  当 future_return_20d <= 0
```

若截点或未来日期的净值不可用、异常且不能由分红解释，则该样本不进入训练和评估。标签口径、净值口径、交易日规则和异常过滤版本必须随模型版本保存。

### 4.2 建模顺序

先从可解释、抗小样本过拟合的模型开始，再以独立时间段验证是否值得增加复杂度：

1. 无模型对照：延续最近 20 日方向、历史上涨频率、始终上涨/始终下跌；
2. 自身走势模型：正则化逻辑回归或等价的概率分类基线；
3. 自身走势 + 市场状态模型：仅当指数特征提高独立样本表现且未破坏校准时启用；
4. 只有在样本量、独立回测和可解释性都达标时，才评估树模型等非线性方法；不能为了追求单次命中率而更换模型。

训练产物必须记录训练数据截点、样本数量、基金范围、特征版本、标签版本、模型版本和随机种子。禁止用大语言模型直接根据基金名称生成预测概率。

### 4.3 对外输出契约

| 字段/状态 | 含义 |
| --- | --- |
| `as_of_date` | 这次判断实际用到的数据截至日，不能写成当前自然日冒充实时 |
| `horizon_trade_days` | 预测窗口，V1 固定为 20 个交易日 |
| `direction_probability_up` | 未来 20 个交易日累计净值上涨的经校准概率；仅在回测达标时输出 |
| `model_kind` | `OWN_NAV_DIRECTION_BASELINE` 或 `OWN_NAV_PLUS_MARKET_V1` |
| `data_completeness` | 各特征组可用性、最新数据日和缺失原因 |
| `explanation` | 仅列数据驱动的正/负向因素及其数据日，不输出交易指令 |
| `DATA_INSUFFICIENT` | 历史长度、关键净值、披露时效或质量不足，不输出概率 |
| `MODEL_NOT_RELEASED` | 回测未通过或尚未完成，不输出概率 |
| `STALE_DATA` | 来源数据超过时效阈值，保留最近结果但显著标明不能据此决策 |

前端统一使用“免费数据方向模型 V1”的名称，并在结果旁显示：截至日期、预测窗口、模型类型、数据完整度、未包含基金持仓/新闻/公告。概率只能表示历史条件下的估计，不能显示成收益率承诺。

## 5. 严格的滚动回测

### 5.1 回测到底在做什么

回测不是把所有历史数据拿来训练后再看自己答得对不对。正确做法是模拟当时的真实状态：

```text
历史截点 t
  -> 只取 t 当天及以前、当时已披露的数据
  -> 训练或更新模型
  -> 预测 t 后第 20 个交易日涨/跌
  -> 等真实净值出现后，与预测比较
  -> 向前滚动到下一个截点，重复
```

这样才能发现“看到了未来”“只适合某一段牛市”“只靠偶然命中”等问题。每次回测必须按时间顺序切分训练、验证和最终独立测试区间；最终测试区间不得用于选择特征、阈值或模型。

### 5.2 覆盖范围与指标

回测要同时覆盖上涨、下跌、高波动和横盘等不同市场阶段，并按基金类型、基金、市场状态分别汇总，而不是只报一个总体命中率。

| 指标 | 要回答的问题 | 防止的误导 |
| --- | --- | --- |
| 方向准确率 | 涨跌方向判断是否比朴素对照更好 | 只报一段好行情的命中率 |
| Brier 分数/概率校准 | 说 70% 上涨时，长期是否真的接近 70% | 概率数字看似精确却不可信 |
| 覆盖率 | 多少基金日期满足数据条件并能作答 | 只挑容易的基金预测 |
| 分组稳定性 | 各基金、市场阶段和滚动窗口是否持续有效 | 个别基金拉高总体成绩 |
| 回撤/波动区间表现 | 高风险阶段是否恶化到不可用 | 平常可用、极端行情误导用户 |
| 相对对照增益 | 是否优于“延续近期方向”等简单规则 | 复杂模型没有真实价值 |

### 5.3 发布闸门

发布不是预先承诺一个漂亮命中率，而是需要在预先冻结的独立测试期满足以下所有条件：

1. 没有未来数据泄漏，抽查任意样本都能还原当时的数据版本和可得日期；
2. 有效样本覆盖多个不同市场阶段，且股票型基金的可评估样本量、基金数和测试窗口已在回测运行记录中固定；
3. 模型在独立测试期相对全部朴素对照存在可重复的增益，而不是只在某一个基金或一个窗口胜出；
4. 概率校准可接受：高概率组不能长期比低概率组更差，校准恶化时必须降级或重新校准；
5. 数据完备度、数据时效和异常净值处理均达到本次运行的质量门槛；
6. 结果页有明确的风险提示、数据边界和“未覆盖持仓/新闻/公告”说明。

若任何一项不满足，系统只能保留回测报告和 `MODEL_NOT_RELEASED` 状态，不能为了产品展示而输出概率。

## 6. 技术架构和运行流程

```text
Tushare 已授权日频/低频数据
          ↓（后台增量、质量校验、数据日期）
fund_ai 数据表与同步运行记录
          ↓（点时特征构建）
feature_snapshot
          ↓（滚动训练与严格回测）
backtest_run ──未达标──> MODEL_NOT_RELEASED
          ↓ 达标
forecast_result（带模型/特征/数据版本）
          ↓（只读 API）
基金详情页 / 关注列表
```

前端负责状态呈现和解释，不计算模型、不持有 Token；Java 服务负责业务接口、权限和任务编排；Python 服务负责可重复的特征计算、训练和回测。所有任务使用已有的来源注册、同步运行、特征快照、预测结果和回测运行等对象扩展，新增表和字段通过版本化迁移落地。

## 7. 版本与实施包

| 包 | 内容 | 结果 |
| --- | --- | --- |
| A. 数据底座 | 落地上一份文档的 P0 回补、增量、水位、异常清单和指数参考数据 | 可追溯的免费数据基线 |
| B. 特征层 | 构建点时净值、经理、份额、分红、档案和可选市场状态特征 | 每个截点可复现的 `feature_snapshot` |
| C. 回测层 | 实现朴素对照、时间滚动、指标、校准和结果留档 | 可审查的 `backtest_run` |
| D. 发布层 | 仅将通过发布闸门的模型写入 `forecast_result` | 明确数据日与模型边界的概率结果 |
| E. 页面层 | 在详情页和自选页展示状态、概率、解释、数据完整度和限制 | 用户不会把结果误解为实时持仓或投资建议 |

各包都可独立验证。A 未完成时不能把缺失数据伪装成特征；C 未通过时不能执行 D；详情页不可绕过 D 直接计算或调用外部数据源。

## 8. 七维治理、风险与验收

| 维度 | 设计要求 |
| --- | --- |
| 业务 | 定位为信息辅助和历史条件概率，不输出买卖指令；模型类别和适用基金范围要公开 |
| 数据 | 严守点时可得性，分红/异常净值处理可追溯，低频披露缺失不补零 |
| 接口与性能 | 训练和回测离线批处理，查询接口只读已发布结果；按基金、日期分页处理，避免全表加载 |
| 权限与安全 | 不使用未授权持仓、新闻、公告；Token 只存在服务端配置；公共模型与用户资产数据隔离 |
| 兼容 | 未上线前保留现有详情页行为；新增模型状态让旧客户端安全降级 |
| 运维 | 每次预测、特征和回测都保存版本、数据截至日、运行状态和失败原因；过期或失败必须可见 |
| 测试 | 覆盖未来泄漏、缺失低频披露、分红跳变、异常净值、指数缺失、回测失败、模型降级和前端风险文案 |

### 最终验收口径

这套方案的成功标准不是“每次猜中”，而是：用户能看到数据确实覆盖到了哪里、模型在看不到未来的条件下经过了多少历史验证、概率是否经校准、以及当前结果何时应当明确拒答。只有这四件事同时成立，免费预测功能才值得上线。

## 9. v1.1｜已确认的 V1.0 最小实施范围（2026-09-02）

为避免把“最终多周期产品目标”和“第一轮可验证试点”混为一谈，现确认：

1. V1.0 仅覆盖 `STOCK` 股票型基金，预测窗口固定为 20 个有效净值日；混合、债券、货币、其他类型和 ETF/LOF 均不输出概率。
2. V1.0 首先只使用基金自身历史净值，模型类型固定为 `OWN_NAV_DIRECTION_BASELINE`。市场指数目录不等于市场特征；在登记白名单、回补指数日线并证明独立增益前，不启用 `OWN_NAV_PLUS_MARKET_V1`。
3. 完整概率仅在“我的关注 -> 单基金详情”中向已关注用户展示；公共基金详情保留基础事实和受限状态摘要，不能绕过关注关系读取概率。
4. 这一试点不取消后续 5/10/20/40 个交易日四周期目标。V1.0 通过发布闸门后，才将相同的点时数据、独立回测和独立发布规则逐周期扩展。
5. 首次实际开发按“手算样本 -> 历史逐日特征 -> 朴素对照 -> 小型概率模型 -> 滚动回测 -> 发布读取”顺序推进；每个阶段均可暂停复核，回测未通过不允许发布。

详细的学习式实施步骤、数据可得日期规则和测试用例见[实施手册](../implementation/free-data-prediction-v1.md)。

## 10. v1.2｜阶段2的HTTP纯计算预览（2026-09-07）

新增 `POST /internal/v1/features/historical-nav-samples/preview`，挂在Python现有features路由，沿用`X-Service-Token`认证和拒绝`Origin`策略。维护人员通过Postman调用，没有Java/Vue用户入口。输入单基金1–512条净值，日期严格递增、无重复，数值有限且为正；输出特征、离线标签、状态和计数，无数据库/外部I/O。

本预览中的`as_of_date`是样本的**净值业务日**；可得截止日为该起点`ann_date`，输出为`available_at`。请求最外层可选`as_of_date`仅筛选结果，不能用本文早期“available_at > as_of_date 一律不可用”的说法直接比较这两个不同语义的字段。公告只有日期，按公告日结束后可用解释；盘中可得时刻和历史修订版本仍未完成。

每条样本只用当时可见的最多61条净值决定输入口径及特征，再附加后20条净值的标签。标签缺值或未成熟仍保留已有特征，不能切换过去口径。特征版本为`M3_STOCK_HISTORICAL_NAV_FEATURE_V2`，未来标签不参与特征哈希。标签窗口出现无效记录时拒收，不跳过后延终点；标签可得日取所需未来记录最晚公告日；起点公告时终点答案已知的样本拒收。

HTTP 200可以包含数据不足状态；格式/顺序/数量错误为422；认证失败/浏览器来源为403；未配置服务Token为503。无持久化、无DDL/DML。同步预览限制512条，日志记录TraceID、基金、计数和耗时；异常保留堆栈，不打印请求体或Token。

说明和JSON/Postman集合在Python仓库`docs_zhx/implementation/historical-nav-http-preview.md`及`docs_zhx/examples/`。此入口不代表分页读库、持久化、真实来源水位校验或模型训练已完成。

### v1.3｜GET直接读库预览（2026-09-07）

同路径新增GET，参数`fundCode`与`asOfDate`，无请求体，直接返回单条HistoricalNavSample。复用内部认证，数据库确定启用股票型基金及已启用、成功同步的来源；净值按该来源隔离。读取起点、此前最多60条截至起点公告日已可见的记录，以及此后原始序列的20条记录；未来不按公告日过滤，以免偷换终点。

### v1.4｜单基金小范围分页只读dry-run（2026-09-07）

继承内部Token/拒绝Origin认证；数据库核验启用股票型基金与就绪来源，无Java/Vue产品入口。

响应固定`mode=DRY_RUN`，返回基金/日期范围、`page_size`、非空`page_count`、`sample_count`、三种质量计数、
`unavailable_reasons`及日期递增的全部`items`。每项与单日GET相同；空范围200且0条，不向邻近日回退。
页大小改变时，仅分页元数据允许变化；同一数据/来源运行记录/计算版本下，样本内容及统计必须一致。

一请求一个REPEATABLE READ、READ ONLY事务，基金/来源仅检查一次。按`nav_date > 上页最后日期`做游标分页，
每页最多两条净值SQL：取起点；将各起点的历史LIMIT 60及未来LIMIT 20子查询通过UNION ALL合并读取。
各查询固定同一基金和来源；历史按各自公告截止筛选，未来不筛公告/数值。辅助数据可越过请求范围和页边界；
每份最多81条输入，调用原构建器只取本起点输出，累计输出最多31份。不一次加载全基金历史，也不逐日网络查库。

复用2连接预览池及5秒单SQL超时，增加15秒页间预算（不是HTTP硬截止）。故障或超时整次503，不返回部分成功；
基金不存在404，品类/来源不适用409，计算数值异常422。只记录一次完成摘要和带TraceID的异常堆栈，不打印Token或净值明细。
无样本持久化、DDL/DML、任务调度、外部采集、模型训练；历史修订回放和来源整日漏数识别仍未完成。

### v1.5｜样本起点新鲜度检查（2026-09-07）

L2局部规则变更：从“终点已知才拒收”收紧为“起点公告时已有任何更新净值已公告即拒收”。
更晚记录必须满足同基金、同来源、`newer.nav_date > anchor.nav_date`且`newer.nav_date <= newer.ann_date <= anchor.ann_date`。
同日公告按日终已知解释，缺失/早于净值日的公告不作已知证据；不依赖净值涨跌方向或人为天数阈值。

- 数据读取：起点SELECT附带相关`EXISTS`（是否存在）布尔值，搜索到起点公告日为止，不限后20条或请求日期段，不新增逐日网络查询。批量仍每个非空页最多2条净值SQL，每份最多81条净值资料。
- 公共计算：`HistoricalNavSampleInput.stale_anchor_dates`是仓储额外确认的过时起点集合，仅内部传递，不开放为HTTP参数。构建器另对所给序列从后向前检查一次，再合并该集合；因此POST也使用同一规则，但无法证明调用者未提供的记录。
- 拒收顺序：先检查起点自身公告日期，再检查是否过时，之后才计算历史指标和标签。过时项保留业务日期/公告日，`nav_value_basis=UNDETERMINED`、`metrics=null`、`offline_label=null`，总体及特征质量均为`DATA_INSUFFICIENT`，原因为`STALE_NAV_AT_CUTOFF`。
- 兼容与追溯：响应新增`sample_rule_version=HISTORICAL_NAV_SAMPLE_RULE_V2`；无此字段的旧响应按旧规则V1理解。它不进入`feature_payload`，指标公式版本仍为`M3_STOCK_HISTORICAL_NAV_FEATURE_V2`，标签仍为`FUTURE_UP_20D_V1`，正常样本原有字段及哈希保持一致。旧起点即使终点已公告也优先使用新的过时原因。
- 安全与运行：现有Token、Origin拒绝、来源隔离、只读一致性事务、超时/连接上限及日志TraceID不变。批量在`unavailable_reasons`汇总新原因，不在循环内增加INFO日志；失败仍不返回部分成功。
- 验收：覆盖部分后续净值已知、仅第21条先公告、同日边界、错误来源/基金、长间隔但无更新公告、日期错误优先级、原始记录不变与分页/单日一致。

这道检查只防止选用旧起点；不证明来源的`ann_date`就是首次可得日期，也没有恢复历史修订版本。保存训练集、训练与发布继续暂停在后续阶段。

#### 三表字段契约

- `historical_nav_sample_batch`：`batch_id UUID`主键，`request_key UUID`唯一且由未来调用方显式提供；`fund_code varchar(32)`关联基金档案；`fund_type varchar(32)`固定STOCK；`source_code varchar(64)`为来源快照；`source_sync_run_id UUID`可空并关联来源运行；`start_date/end_date date`；`feature_version/sample_rule_version/label_version varchar(128)`非空；`purpose varchar(32)`固定LEARNING_ONLY；四个质量计数为integer；`unavailable_reasons jsonb`为原因到数量的对象；`created_at timestamptz`为保存时间。
- `historical_nav_sample`：`sample_id UUID`主键，`batch_id UUID`关联批次，`as_of_date date`与批次组成唯一键；`available_at date`可空；`nav_value_basis/eligibility_status varchar(32)`；`unavailable_reason text`可空；`feature_payload jsonb`；`feature_hash varchar(64)`。同批共享基金、来源和规则，未来服务核对载荷中的重复元数据与封面一致。
- `historical_nav_sample_label`：`sample_id UUID`同时是主键和题目外键；`horizon_trading_days smallint`固定20；`label_end_date/label_available_at date`；`future_return_20d numeric`不固定小数位，保持现有Decimal值；`label_up_20d smallint`为1/0。所有列非空，缺答案通过没有行表达。

数据库结构声明：日期差0–30；计数非负、总数不超过日期范围且等于三种状态数之和；JSON顶层为对象；哈希为64位小写十六进制。
完整样本无拒收原因，其余状态必须有原因；非DATA_INSUFFICIENT要求有效可得日期与已确定口径。
拒收行允许公告为空或早于业务日，不能为了满足约束而改写错误事实；标签收益须有限且大于-1，上涨1与非上涨0必须与收益符号相符。
外键不配置级联删除。`feature_hash`只覆盖已有特征包，不含标签、批次编号或独立筛选规则版本；不保证整个批次内容相同。

以下为**下一步保存服务必验规则，当前未实现**：题目日期在批次范围；基金/来源运行归属/三个版本一致；特征不混答案且哈希匹配；数量/原因统计与明细相符；仅SCORABLE有且必须有答案，标签终点晚于起点且标签可得日晚于输入截止；输入与标签口径一致。当前读库保存场景仍应拒绝未就绪来源，不因水位列可空而放宽现有准入。
重试与重算区别：同`request_key`先校验原请求身份，同请求返回旧批次，即使来源随后更新也不重新计算；请求身份不含`pageSize`。想使用新源数据或新规则，必须明确提交新凭证。凭证相同但基金/日期/规则不同应冲突拒绝，而非静默返回错误批次。
整批提交或整批回滚、不覆盖旧批次、未来标签成熟生成新批次，由后续事务代码实现；当前没有触发器/权限来提供数据库层绝对不可变保证。
