# 基金经理模块完整实施方案

日期：2026-10-26，北京时间。状态：已完成三端首期实现与本机验收；数据覆盖和专项验收限制见[实施记录](../implementation/fund-manager-module-2026-10-26.md)。

本方案让用户从顶部菜单查找基金经理，查看职业履历、在管与历史管理基金，再进入具体基金查看任期表现。沿用现有 Vue → Java → Python 链路和绿色工作区布局。

“实时”采用披露驱动的更新方式：页面读取最新已核实资料，后台按日核查，并在取得有效变更公告后更新相关事实。经理履历、基金净值、净资产和持仓分别保留各自日期，不承诺供应商未提供的秒级更新。

本文件保留设计基线；用户随后授权实施。本机已执行新增迁移、三端代码、来源核对与浏览器验证，未修改日常自动化配置，未提交或发布生产。以下基线查询描述的是实施前状态，当前数据以实施记录和回查时间为准。

### 1.2 本模块的完成范围

- 提供已收录经理的搜索、列表、详情和基金双向跳转。
- 从当前基金范围提取经理线索，补查这些经理在现有授权来源中的其他任职关系、关联基金基本资料和职业履历。
- 区分在管、离任、未来任职、待核对和存在冲突的记录。
- 对资料满足条件的具体基金，计算可追溯的任期表现；其他项目保留缺项。
- 展示管理规模、披露持仓和经理动态时，逐项满足本方案的数据门槛。
- 首期目录称“基金经理”，说明“已收录范围”；不称“全市场经理大全”，不推出未经验证的经理总分、全市场排名或个人收益曲线。

新增经理关系不自动增加关注、不处理交易，也不自动将相关基金加入持仓、预测、评级、费率或日常净值任务。

## 2 页面结构与交互

### 2.1 顶部菜单和路由

顶部顺序：基金市场 → 基金经理 → 我的关注 → 我的持仓 → 持仓分析 → 站内提醒。

| 路由 | 用途 | 权限 |
| --- | --- | --- |
| /fund-managers | 经理目录，保存姓名、公司、页码等查询条件 | 已登录且有 FUND_READ |
| /fund-managers/:managerId?section=funds | 经理详情，默认展示在管基金 | FUND_READ |
| /fund-managers/:managerId?section=history | 历史任职 | FUND_READ |
| /fund-managers/:managerId?section=profile | 职业履历 | FUND_READ |
| /fund-managers/:managerId?section=performance | 任期表现 | FUND_READ |
| /fund-managers/:managerId?section=disclosures | 相关披露和经理变更 | FUND_READ |
| /fund-managers/:managerId/funds/:relatedFundId | 尚未纳入原基金市场的关联基金基础详情 | FUND_READ，且经理与该基金关系可见 |

沿用 usePageNavigation 的左侧分区。经理详情不再叠加第二套同义导航，不把履历、在管基金和收益全部堆到首屏。

现有基金详情和关注详情中的经理姓名增加链接。使用服务端返回的 managerId，不用姓名拼路由。尚未消歧的记录不能跳到任意同名人的档案。

返回目标仅接受站内白名单路由、已知参数和受限长度，保留原筛选、section、页码及浏览位置，避免任意 URL 跳转。

### 2.2 经理目录

默认展示具有已核实任职关系的已收录经理；尚待确认的线索在后台核对，不以确定人员身份参与数量统计。无现任记录但有历史任职的经理可通过“含历史任职”筛选查到。

首屏保留：姓名、已核实任职公司或关联公司、学历、已收录在管产品数及份额数。产品对应关系未核实的行只展示份额数，不猜测独立产品数。

支持姓名、基金公司、在管/历史状态和基金类型筛选；默认按姓名和稳定编号排序。每页 20 条，最大 50 条。不默认按未经统一计算的“收益最高”“最强经理”等排序。

“我关注基金的经理”和“我持有基金的经理”作为后续个人筛选功能，由 Java 依据当前会话计算，分别验证关注或持仓读取权限。公共目录功能不依赖这些个人筛选。

本地无结果时说明“暂未收录相关经理”。普通搜索不直接访问供应商、不创建采集任务，也不将“未收录”解释为这个人不存在。

### 2.3 经理详情

| 分区 | 展示内容 | 展示条件 |
| --- | --- | --- |
| 页首 | 姓名、任职公司或关联公司、学历、资料核对日期 | 各项独立保留来源和日期；不确定当前雇主时只写关联公司 |
| 在管基金 | 基金名称、代码、份额、管理起始日、共同管理情况、可用的任期表现 | 在任关系已核实；个人名下查询结果不等于完整共管名单 |
| 历史任职 | 按时间倒序列出基金、任职起止日、可核对表现 | 已离任且有有效日期；离任原因只采用明确公告 |
| 职业履历 | 教育、投资管理相关从业经历、经核实的专业资格 | 原文可追溯；无依据不填证券从业年限 |
| 任期表现 | 选择具体基金、任期和可核对阶段，查看收益及最大回撤 | 通过第 6 节的数据门槛 |
| 相关披露 | 经理变更、管理基金公开报告及必要原文链接 | 确认基金与经理任期关系，显示公告日和报告期 |

管理规模和投资偏好为条件展示内容：条件不满足时不放空的 KPI 卡片，不以零值填位。资料不足在对应分区用一句话说明。

A/C 等份额关系核实后按产品归组、展开份额，但各份额的净值、收益和费率仍分别展示。未核实时分列并标明已收录范围。

### 2.4 基金详情的落点

已在原市场目录且满足原查询条件的基金，沿用现有 /funds/:fundCode；从关注页进入的本人关注基金仍可返回原关注详情。

新发现的外部份额先进入关联基金基础详情，展示已核实名称、代码、类型、公司、任职关系及已有净值。净值未取得时明确“暂无净值资料”，不能将用户带到 404，也不能借用同产品其他份额净值。

关联基金详情不提供无实际支持的关注、交易或刷新按钮。是否正式纳入原市场数据范围走单独的管理员维护入口。

## 3 数据来源与补齐范围

### 3.1 来源职责

| 来源 | 使用内容 | 边界 |
| --- | --- | --- |
| 现有 fund_manager | 姓名、学历、简历、基金代码、任职及离任日期 | 接口未给人员唯一 ID；按姓名命中后仍需消歧 |
| 现有 fund_basic、基金基础资料 | 基金名称、类型、管理公司、生命周期 | 公司名称不是经理姓名，不据名称相似认定产品家族 |
| 基金公司官方页面和正式披露 | 职业履历、任职变更、主代码与份额关系 | 复用已有原件和目录；转载必须保持来源属性 |
| 现有净值及分红资料 | 具体份额任期表现 | 不跨份额借数，不用累计净值比值冒充含分红总回报 |
| 现有定期报告 | 产品净资产、披露持仓和管理说明 | 报告期、公开日、取得时间分别保存 |

本次重新查阅的官方能力说明：[基金经理接口](https://tushare.pro/document/2?doc_id=208)、[基金净值接口](https://tushare.pro/document/2?doc_id=119)。接口说明支持按姓名、代码和公告日查询经理、offset/limit 分页及 resume 字段；基金净值含单位净值、复权净值和资产净值字段。具体单位、复权方法和本账号字段覆盖仍逐项验收。

沿用当前已授权且启用的数据源，不因公开文档列出某个接口就自动调用未授权接口。只保存职业相关公开资料，不新增出生年份、性别等与当前用户任务无关的字段。

### 3.2 初始补齐流程

1. 冻结当次市场范围、来源、经理线索和已有原件版本，保存输入摘要；95 个姓名仅作为线索，不预先当作 95 位已确认人员。
2. 对每条线索建立本基金任职锚点，按姓名读取供应商的全部可取得分页，取得职业简历。
3. 对候选关系关联基金基本资料，结合公司、任期、职业经历和正式资料进行人员消歧。公司和姓名相同只能作为线索，不能单独作为身份结论。
4. 对已确认人员整理当前与历史任职；有歧义的记录保存候选关系，不进入确定在管数量。
5. 按来源代码去重补关联基金基本资料；需要计算任期表现的基金再补其经理团队、净值、分红和估值日历。
6. 生成经理资料覆盖快照，按第 5 节原子发布。

扩展深度固定为“目标经理 → 其关联基金”，不继续遍历这些基金的其他经理、再遍历其他经理的基金。共管人员可作为本基金团队事实保存，不能自行变成下一层采集种子。

公开披露来源的 10 只基金先从已有正式报告和公告提取经理线索；需要对照 Tushare 时保留来源关系，不覆盖原 source_code 或改变原日常任务范围。

### 3.3 分页与覆盖证明

- 供应商每页最多 5,000 条，按 offset/limit 逐页读取。首次空页表示该次查询无返回记录，不能直接解释为人员不存在或全部离任。
- 每次最多 20 页；达到保护上限、重复页、结构错误、网络失败或扫描期间结果明显变化时记录不完整，禁止标记“完整取得”。
- 保存参数摘要、页码、取得时间、条数和响应哈希；姓名参数使用绑定或结构化请求。
- 页面读全、人员身份核实、产品家族核实、共管团队核实、完整职业生涯覆盖是不同结论，不能互相替代。
- 来源缺少固定排序和一致快照保证时保留扫描区间；变化检测只帮助发现不稳定，不作为证明来源全部历史完整的依据。
- 默认使用“已收录 X 个份额”。只有资料范围、身份和产品关系均有可核对依据时，才提供该范围内的产品统计；不宣称供应商未证明的全市场完整性。

## 4 人员身份和任职事实

### 4.1 身份规则

经理使用系统内部 UUID。姓名、任职公司和来源展示名均可变化，不作为永久自然主键。

身份确认优先使用正式披露中的明确职业身份及对应基金经历。若来源没有人员编码，必须保留用于归并的职业经历、任职交叉事实和原文证据；单凭同名、同学历、简历文本相似或同公司不自动合并。

无法确认时创建独立候选或保留待核对关联，不能随意拼到已存在档案。人员合并、拆分保留操作审计、依据和旧编号重定向；拆分后重新计算受影响的数量和表现。

现有 fund_master.manager_name 实际承载基金管理公司，不能当作基金经理姓名来源。

### 4.2 任期与修订

- 任职日已生效、未有有效离任事实且无身份或来源冲突时，才作为“已核实在管”。未来任职单列为待生效。
- 离任日为空还要检查采集覆盖、是否有后续公告和来源冲突，不能永远沿用旧的空结束日期。
- 同一人员多次管理同一基金按不同任期分别保存；总任职天数使用区间并集，避免重叠重复计算。
- 任期开始未知、结束早于开始、公告与供应商冲突时保留待核对，不产生确定收益。
- 一次完整响应没有再列出某条关系，只能产生“本次来源未列出”的核对项；不能直接删除历史或认定已离任。
- 确认的离任或纠错发布为新版本，旧事实及其证据保留。旧指标立即退出当前展示，待按新任期重新计算。

规范任期采用开始日、最后管理日均包含的日期区间；当日是否在任按 begin_date ≤ 当日且 end_date 为空或 end_date ≥ 当日判断。供应商结束日期与公告离任生效日的语义可能不同，原值和字段含义均须保留；只有明确依据支持时才换算最后管理日，不统一机械减一天。

当前 source_record_key 包含任职/离任日期，来源补上离任日可能产生另一个键。因此不能把既有每一行直接当作独立有效任期，也不能简单累加 end_date 为空的行。

### 4.3 共管和规模去重

通过该基金完整的经理任职区间计算共管团队；只查询一个经理姓名取得的记录不能证明独立管理。

产品归组须有正式主代码、合同或报告中的份额关系证据。现有 fund_master_id 的存在本身不是经核实的 A/C 去重依据。

共同管理期间不按人数平分收益或管理资产。经理名下资产仅表示其参与管理的产品规模，不能将所有经理名下规模再相加作为市场总资产。

所有 evidence_ref 使用受控的原件标识、来源 URL、公开日、取得时间和内容哈希。原件文件沿用项目保存/哈希留档能力，新建经理资料命名空间，不把全部经理硬编码到 fund-exposure-002112 目录。路径由服务端生成，客户端不得提交本机文件路径。

product_identity 是有固定 JSON 结构的产品映射证据，包含主代码、关联份额、适用期、来源及验证结论。产品映射变更时保留版本；若后续有独立公共产品主档，按相同契约迁移，不能直接改写历史统计。

### 5.2 兼容原表与运行记录

- 原 fund_manager_assignment 继续供旧详情读取，不删除或重写历史；新模块从其导入原始观察，通过 canonical 任期版本去重和消歧。
- 完成迁移的基金详情优先读取已发布的规范任期，再映射回原响应字段；未迁移基金保留原读取路径和缺项说明。同一页不能拼接两套当前经理名单。原同步取得新任职观察时登记相关快照待复核，防止新经理页与基金页长期显示相反结论。
- 原 FundManagerResponse 增加可空 managerId、身份可见性和资料版本字段；原有姓名、学历、日期字段保持含义。待核对身份不返回可误跳的确定人物链接。
- 在途 tenurePerformance 契约中的 returnRate 保持小数比例，保留 startDate、endDate、reason、includesCoManagement 和 calculationBasis。新经理接口也使用相同语义，不再另造同名但单位不同的百分比字段。
- source_sync_run 设计增加可空 scope_snapshot jsonb 和 result_summary jsonb，保存目标经理范围、各阶段结果和覆盖计数；旧任务和历史记录可不填。
- 索引以 manager_id、related_fund_id、当前任期、来源代码和发布时间为主；初始人员规模很小，姓名绑定参数搜索先沿用普通查询，不为此强制安装全文检索扩展。

### 5.3 采集与发布事务

1. 取得任务互斥并冻结目标范围，网络请求放在数据库写事务外。
2. 按页保存响应原件及哈希；校验后将本经理的身份依据、资料版本和任期候选写入短事务。
3. 核实身份、日期、关联基金和冲突；生成引用确切版本的经理快照。
4. 在同一短事务内切换本经理快照、更新目录快照引用，并使旧任期指标失效；提交后增加公开版本号。
5. 成功的经理可独立发布，失败的经理保留上次有效快照和当前缺口；整批结果如实为部分成功。

履历、业绩等可选资料缺失不抹掉已核实的在管关系。核心关系不完整时不得发布“完整在管列表”。失败、空响应或无权限不能覆盖上次成功核对时间。

列表分页绑定目录快照；经理详情和基金表绑定该经理快照。版本已过保留期时返回明确的快照过期原因，前端重新读取第一页，不拼接新旧分页。

## 6 统计与业绩计算口径

### 6.1 数量与任职时间

| 指标 | 口径 |
| --- | --- |
| 在管份额数 | 截止日已核实有效的不同 related_fund_id 数量，不按任期版本行数计数 |
| 在管产品数 | 只在产品家族映射完整时按有效主代码去重；否则为 NULL 并展示份额数 |
| 历任基金 | 已核实离任关系按产品/份额分层展示，多次任职区间分别保留 |
| 本基金累计任职天数 | 有效日期区间的自然日并集，展示是否含共同管理；未知区间只允许明确“至少” |
| 完整从业年限 | 仅采用可追溯职业履历/正式资料；不能以本库最早任职日代替 |

日界和任务截止使用 Asia/Shanghai；数据库时间戳存 timestamptz。任职日是业务日期，不根据数据库时区显示结果擅自偏移一天。

### 6.2 任期表现

计算对象为“具体份额 + 具体经理任期 + 共同/独立管理区间”。不将多个基金收益简单平均成个人收益，不提供未定义组合权重的经理总收益曲线。

- 截止日取已公开且在实际取得截止前可用的净值日，并受离任日期限制；未来生效任职不计算。
- 起点沿用现有计算约定，使用任职日起首个有效估值日的收盘净值；这不会把交接日整天收益归给经理。界面显示实际计算起止日。
- 终点使用截止范围内最后一个有效估值日净值；不同基金按各自估值日历和披露延迟处理，不统一套用 A 股交易日。
- 主计算沿用在途 CASH_REINVESTED_NAV_V1：G_0 = 1，G_t = G_(t-1) × (当日单位净值 + 当日每份已实施现金分红) / 前日单位净值；首日收盘前所属派息不重复计入。先核实每份金额单位、生效日和币种，不根据字段名称猜测换算。
- 使用累计净值与单位净值之差核对现金变化，复权字段用于检查无法解释的折算/拆分；两者都不直接替代主计算的收益分子分母。不能用累计净值比值冒充总回报，也不能在缺分红时静默切换成另一口径。
- 区间收益 = G_end / G_start − 1；保存和接口返回小数比例，前端仅乘 100 一次后显示百分比。只有“复权净值字段存在”不足以认定完整任期可算。
- 最大回撤 = 该再投指数区间内 max(1 − G_t / 此前峰值)，保存非负小数比例，前端显示非负跌幅百分比并写“最大回撤”。
- 年化 = (1 + 区间收益)^(365 / 实际自然日跨度) − 1；仅完整可核对且不少于 365 个自然日时展示；短期不强制年化。
- 任期净值早期缺失时只能展示明确标日期的“可核对区间表现”，不能仍叫“完整任期回报”。未知交易日、关键缺值、数据冲突或无效净值时保留 NULL，不前向填充。
- 共管与独立管理分别统计。只有完整团队证据支持的区间才能叫独立管理；共管收益不按人数分摊。
- 该统计反映基金份额净值表现，不包含个人申赎时点和交易费用，不等于投资者实际收益。

计算前还须证明本基金、本来源、有效检查周期内的分红资料完整；不能只凭存在任意一条全局 MARKET_DETAIL_DIVIDEND 成功记录就认定所有基金均已补齐。拆分、折算或同日多条分红无法解释时保留不可计算，不放宽阈值凑出回报。

优先复用在途 fund_manager_performance 服务和仓储，并补齐本基金分红覆盖、已发布任期版本与输入快照绑定。当前读取上限为 5,000 条净值、100 条分红，超限应保持不可计算；需要扩大覆盖时采用有界分段读取和完整性校验，不能截断后仍标“自任职以来”。其当前日历和基金类型支持范围也不能无条件扩展到 QDII、货币、FOF 或所有公开披露基金。

原 fund_information_manager 的 002112 专用分析按其冻结方法继续留存，不与新页面结果混算；若要对照两种方法，先证明相同份额、区间、现金事件和方法等价性。图表可下采样，计算不得用下采样数据。

同类排名、基准超额和风险调整收益暂不进入默认指标；待历史分类、独立产品样本、基准序列和统一日期验证后另行启用。现有基金评级不转换成经理评级。

### 6.3 管理规模

只使用口径、币种、产品范围明确的净资产，不用份额数量代替金额。同产品 A/C 等份额合计规模仅计算一次，不能重复累加 total_netasset；基金净资产也不能再叠加其所持证券市值。

总规模要求已核实完整产品范围、同一报告日、可比较币种和已去重资产。缺项时最多展示“已核对产品规模小计”，同时标日期、覆盖产品数及缺项；总产品数未知时不编造覆盖百分比。不引入未授权汇率或静默折算币种。

### 6.4 投资偏好与动态

仅描述“管理基金在某报告期披露的行业/资产分布”，不声称这些就是经理当前实时持仓或个人全部投资偏好。任职中途接手、共管、仅季报前十持仓等边界必须保留。

经理变更公开原因按原公告展示，不推断离职隐情或未来收益。履历摘要不得超出原件；如后续使用现有模型整理文字，身份匹配、日期和统计仍由确定性校验决定，不由模型补缺。

### 7.3 错误、降级和权限

- 401/403 继续使用原认证授权处理；所有 GET 均需 FUND_READ。
- 400 用于参数错误；404 用于对象或关联不存在；采集任务互斥冲突返回 409；分页快照过期同样使用 409 并明确 SNAPSHOT_EXPIRED 原因，前端重新取第一页；来源或服务故障且无有效历史资料时按既有服务错误契约返回。
- 普通资料缺项返回正常业务响应及明确可用状态，不全部包装成系统故障，也不伪装查询成功但返回零。
- 公开经理资料可按版本缓存；个人关注标记和个人筛选不进入共享缓存。Java 批量追加当前用户状态，避免逐行查询。
- Python 暂时不可用时，可使用 Java 最后一次成功的纯公共资料缓存，保留其真实核对时间并标记过期；Redis 不可用仍可走主只读服务。
- 返回路径、来源链接和正文均作协议白名单/安全文本处理；来源 HTML 不直接渲染，避免开放跳转、脚本注入和越权文件读取。

## 8 更新机制和时效目标

### 8.1 默认更新安排

| 数据 | 建议更新方式 | 时效说明 |

| 已登记经理的当前与历史任职 | 每日执行独立经理资料任务，全量核对目标经理的已知来源关系；失败项留待重试 | 不只按公告日游标增量，防止遗漏旧任期被补写离任日期 |

| 净值和分红 | 原净值任务完成后，对受影响经理任期指标执行本地重算 | 页面跟随已披露净值；不生成盘中估算替代官方净值 |

| 页面数据 | 打开页面读取已发布快照；页面可见时每 60 秒检查版本，版本变化再读取当前分区 | 页面隐藏/卸载停止轮询；错误退避；不会触发采集 |

当前已有北京时间 00:30 的统一日常自动化入口，不另建第二个夜间定时器。实施时选择将 FUND_MANAGERS 作为原 MARKET_ALL 的最后一个阶段，复用既有执行器、来源互斥和结果持久化；也保留管理端独立更新入口。不修改自动化配置，既有入口下次实际执行总批次时才会包含新阶段。

该安排依赖现有本机自动化和执行环境可用。未唤醒、服务未运行或任务未完成时保留真实资料日期，不假装已经日更；恢复后按原有效范围补查，不伪造过去的取得时间。若另有全天候更新要求，需要常驻执行环境，本方案不默认新增服务器或部署成本。

实施决策修订：原方案拟在总批次外追加一次独立调用；实际接入原阶段列表，避免修改自动化提示或增加第二套调度。分母从实际阶段列表计算，当前增加一项经理阶段；原有阶段顺序、分析前置门槛和基金目标范围保持原逻辑。该串行接入已通过批次替身回归，尚未等待下个日常自动化周期的真实回执。

若后续确需更频繁核对，可在同一调度入口增加重点经理每两小时一次的轻量检查，先实测额度、运行时间与来源变更频率；这不是默认已启用能力，也不是秒级实时承诺。

### 8.2 可验收的时效目标

- 本地页面查询目标：在当前单机规模下 P95 不超过 1 秒；通过固定并发和样本实测，不预先写成已达标。
- 核心资料已核实并发布后，正常可见页面在 60 秒轮询加一次请求时间内看到新版本。
- 净值任务结束后，依赖齐备且执行队列可用时，受影响的本地指标重算目标不超过 5 分钟；锁等待与资料缺口单独记录。
- 无法承诺供应商、基金公司或公告平台何时更新。页面分别保留资料核对时间、净值日和报告期，不合成一个虚假的“全部实时更新”。

### 8.3 任务保护和恢复

独立任务继续使用 LocalSyncJobManager 单活动任务和来源数据库咨询锁；不同入口不能绕过锁各自启动采集。记录待处理经理集合时合并去重，在原任务终态后由受控调用方提交，不在状态 GET 中隐式启动。

经理任务采用按经理小批提交。连接 5 秒、读取 20 秒作为初始上限，最多 2 次受控退避重试；429 依来源提示退避并设总等待上限。最终参数沿用现有配置并经实测调整。

使用所有相关入口共享的来源请求预算，经理任务初始最多占 60 次/分钟，且不得超过已核实来源限制。不能认为只在一个新客户端加 sleep 就限制住了全项目。预算耗尽、达到保护页数或执行被中断时保留本轮具体缺口，不报全量成功。

进度与目标范围持久保存。服务重启后沿用现有 SYNC_INTERRUPTED 语义，不能把未完成任务当作成功；下一次明确重试复用已验证原件及已完成经理，不自动补造来源响应。

GET 不触发外部网络，POST 请求结果未知时先查原幂等请求/最近任务，不直接重复提交。新增请求编号需要贯穿 Java、Python 和任务回执，重复请求返回同一任务。

## 12 发布与回滚

先以新增结构和关闭的用户入口部署 Python，再接 Java 契约和只读验证，完成小范围经理数据核对后开放 Vue 入口。个人筛选、规模和业绩可按能力独立控制，但不能让关闭项显示为零或成功。

回滚优先关闭经理入口、停止新增经理任务并回退对应应用代码；保留新增表、原件、原任职观察和历史版本。既有基金详情只使用兼容字段，不依赖新模块在线。

迁移采用新增表和可空字段，不执行清库或破坏性覆盖。存在真实数据后不以 Alembic downgrade 直接删表回滚；结构清理另行评估。发布前确认配置与迁移版本兼容、现有工作区改动边界及当前实际运行任务。
