# 基金雷达：当前 2000 积分可用数据补齐需求

> 关联需求：[基金雷达一期](fund-radar.md)、[自选与预测模块](watchlist-prediction-module.md)
> 关联设计：[免费已授权数据预测 V1](../design/free-data-prediction-v1.md)
> 版本：v1.0 ｜ 日期：2026-09-02 ｜ 变更等级：L3 ｜ 状态：待实施

## 1. 要解决什么

在不继续购买 Tushare 积分、不抓取未获授权网站数据的前提下，把当前账号已经有权限、并且对基金详情和免费预测有直接价值的数据补齐到本地数据底座。

这里的“全部补齐”有明确边界：

1. 补齐当前 2000 积分下、与公募基金、基金净值、基金经理、基金规模和市场环境有关的数据；
2. 补齐已纳入基金雷达支持范围的基金历史数据，而不是把整个 A 股市场、期货、债券、宏观等所有 Tushare 接口无差别下载；
3. 不购买 `fund_portfolio`、新闻或公告权限，也不以爬虫绕开数据授权；
4. “补齐”包括历史回补、持续增量、数据质量标识和可追溯的同步记录，不等于页面上一次性展示所有原始字段。

这样做的目的不是伪造“信息完整”，而是在当前预算内让系统具备一个可验证的、可持续更新的免费数据基线。

## 2. 已核验的当前权限与本地缺口

### 2.1 当前账号的实时最小调用核验

## 3. 数据范围和处理规则

### 3.1 P0：必须补齐并持续维护的数据

| 数据集 | 来源接口 | 历史回补与增量 | 本地落点 | 业务规则 |
| --- | --- | --- | --- | --- |
| 基金基础档案 | `fund_basic` | 全量后按状态和更新时间复核 | `fund_share_class`、`fund_profile` | 保留基金代码、类别、成立日、状态、费率、托管/管理信息；已终止基金不物理删除 |
| 基金公司 | `fund_company` | 全量后每周核验 | `fund_profile` 的管理公司展示字段及可追溯原始记录 | 公司名称变化应当触发档案更新；接口无稳定公司标识时不得自行拼造主键 |
| 单位/累计净值 | `fund_nav` | 从每只基金最早可得日回补，交易日增量 | `nav_daily` | 同时保存单位净值、累计净值、复权口径、来源日期；重复日期按来源更新，异常值需标记而非静默覆盖 |
| 基金经理任职 | `fund_manager` | 全历史回补，每周增量 | `fund_manager_assignment` | 保存经理、任职开始/结束、公告日和当前状态；任职年限必须按预测截点计算，不能用今天的经理信息回填过去 |
| 基金份额/规模 | `fund_share` | 全历史可得日期回补，按披露节奏增量 | `fund_share_snapshot` | 保存份额、数据日期和披露日期；接口没有记录时标为“未披露”，不得补零 |
| 分红事件 | `fund_div` | 全历史回补，按披露节奏增量 | `fund_dividend` | 保留权益登记、除息、派发等日期；仅作事件特征，不把分红当天净值变化误判为亏损 |
| 场内基金行情 | `fund_daily` | 仅限有交易代码的 ETF/LOF 等产品，按交易日增量 | 新增 `fund_exchange_daily` | 与场外净值分开存储；没有交易代码或没有行情不是同步失败 |
| 指数目录和分类 | `index_basic`、`index_classify` | 全量白名单后每周核验 | `benchmark_series`（语义调整为市场参考指数） | 只选取宽基、成长/价值、行业等已批准的指数；指数是市场背景，不是另一只基金的替身 |
| 指数日线 | `index_daily` | 从选定指数最早可得日回补，交易日增量 | `benchmark_nav_daily` | 保存收盘价和交易日期，用于构造市场涨跌、波动和风格状态 |
| 指数权重 | `index_weight` | 按指数权重公布频率回补和增量 | 新增 `index_weight_snapshot` | 保存权重生效日、成分代码和权重；仅解释指数结构，不能推断某只基金持仓 |

### 3.2 P1：已验证可取，但默认不做全市场入库的数据

`daily` 与 `daily_basic` 当前已验证有权限，但没有基金持仓明细时，无法可靠地把任意股票行情、估值映射为某只基金的特征。因此：

1. 不允许把全市场股票日线和估值数据作为“基金完整持仓数据”入库或展示；
2. 只有当数据通过“选定市场指数成分/公开且授权的明确关联”进入市场参考模块时，才按白名单、小窗口、可追溯的方式采集；
3. P1 数据不作为免费预测 V1 的上线前置条件，避免数据量、成本和维护复杂度膨胀。

### 3.3 明确不在本次范围的数据

| 数据 | 原因 | 系统行为 |
| --- | --- | --- |
| `fund_portfolio` 基金股票持仓 | 当前 Token 无权限，需要更高积分 | 页面明确显示“当前免费数据未覆盖基金持仓”，不作猜测 |
| `fund_adj` 等高积分复权能力 | 当前 Token 无权限 | 不把未授权字段写入模型或页面契约 |
| 新闻、公告 | 用户不购买相应独立权限 | 不爬取、不展示为实时新闻，也不纳入 V1 特征 |
| 分钟级/实时行情 | 不属于当前免费、端到端可验证的范围 | V1 仅使用有明确数据日的日频数据 |
| 用户个人买入金额、持仓成本 | 与“基金买了什么股票”和公共预测无关 | 不进入公共预测特征；未来个人投顾功能需单独授权与隐私设计 |

## 4. 同步和数据质量要求

### 4.1 执行方式

同步只能由后端批处理任务发起，基金详情页、关注列表和预测查询接口均只读本地库，绝不在用户打开页面时调用 Tushare 或触发大规模回补。

```text
基金范围白名单
  -> 分段历史回补（按基金/指数/日期窗口）
  -> 幂等写入与质量校验
  -> 记录 source_sync_run、水位和异常
  -> 日常增量同步
  -> 触发特征重算候选（不等于立即发布预测）
```

全量和增量都按稳定业务键 `MERGE`：基金类按“来源基金代码 + 数据日/事件日”，指数类按“来源指数代码 + 交易日/权重生效日”。不允许常规任务清表重灌；上游更正时更新来源时间、行摘要和业务更新时间。

### 4.2 建议频率和水位

| 作业 | 建议频率 | 水位 | 失败处理 |
| --- | --- | --- | --- |
| 净值、场内基金日线、指数日线 | 每个交易日数据可得后 | 各代码最后成功交易日 | 单代码失败可重试，不能推进该代码水位 |
| 基金档案、基金公司 | 每周一次，必要时人工触发 | 最近成功校验时间 | 保留旧值并记录待核验，不清空展示 |
| 基金经理、份额、分红 | 每周一次；公告高峰可加密 | 各基金最近成功数据日/公告日 | 空结果与请求失败必须区分 |
| 指数目录、分类、权重 | 每周目录复核；权重按公布节奏 | 指数代码 + 最新权重生效日 | 非交易日或未公布不报为数据错误 |

每次运行必须写入来源、请求范围、开始/结束时间、成功/失败数量、缺失原因、重试次数和数据截至日。日志中不得输出 Token 或完整请求凭据。

### 4.3 数据质量闸门

1. 基金代码、指数代码、日期和来源必须可追溯；日期统一按 `Asia/Shanghai` 解释。
2. 任何价格、净值、份额和权重的非法值必须进入异常清单，不能以 `0` 替代。
3. 净值出现跳变时需与分红/拆分事件共同校验；无法解释时标记为异常，预测特征不使用该点。
4. 基金经理、份额、分红等低频数据必须保存“可获得日期”；回测和预测只能使用当时已经披露的信息。
5. 每个预测对象都要能计算数据完备度和最新数据日；低于模型要求时只能返回“数据不足”，不能输出伪精确概率。
6. `source_registry` 的许可范围要更新为本文件列明且已验证的接口清单，不能继续仅写净值/档案三类；许可变化需保留审计记录。

## 5. 实施顺序与验收

### 5.1 实施顺序

1. 固化基金与指数白名单、来源许可清单和稳定业务键；
2. 扩展迁移脚本，新增场内基金日线、指数权重快照等必要表，并为日期水位建立索引；
3. 先回补基金档案、净值、经理、份额、分红，再回补指数目录、分类、日线、权重；
4. 对每个数据域做覆盖率、日期连续性、重复键和异常值检查；
5. 开启独立的增量任务并观察至少一个完整更新周期；
6. 数据质量达标后，才交由预测 V1 生成特征和滚动回测。

### 5.2 验收条件

| 验收项 | 通过标准 |
| --- | --- |
| 授权边界 | 运行日志和代码配置只使用本文件 P0/P1 已授权接口；没有对 `fund_portfolio`、新闻、公告的请求 |
| 历史完整性 | 白名单内每个基金、指数均有可解释的最早/最新数据日；确无披露的数据明确标记缺失 |
| 增量正确性 | 重跑同一窗口不产生重复行；失败代码不会错误推进水位；上游修订可以更新本地记录 |
| 数据质量 | 唯一键、日期顺序、数值范围、分红事件关联和来源字段通过检查，并输出异常清单 |
| 页面隔离 | 详情页和预测接口不触发外部同步；无持仓权限时如实展示能力边界 |
| 可审计性 | 任一页面字段和模型特征都能追到来源接口、数据日和同步运行记录 |

## 6. 七维治理与风险

| 维度 | 本次约束与处理 |
| --- | --- |
| 业务 | 只补“公共基金信息与市场参考”，不把它包装成基金完整持仓或投资建议 |
| 数据 | 采用点时可得日期、稳定业务键、增量水位和异常清单，防止历史被今天的信息污染 |
| 接口与性能 | 后台批量、分段、限流、重试和幂等写入；前端只读本地数据 |
| 权限与合规 | 仅使用当前授权接口；不存 Token、不爬付费数据、不把个人账户数据混入公共模型 |
| 兼容 | 保持既有基金档案、净值和同步运行记录可用；新增字段和表走版本化迁移 |
| 运维 | 记录数据截至日、任务状态和失败原因；连续失败应告警，不能静默展示旧数据为最新 |
| 测试 | 覆盖历史回补、重复执行、空结果、源端修订、权限拒绝、接口超时、数据异常和页面只读隔离 |

### 需要持续说明的限制

即使 P0 数据全部补齐，系统依然不知道基金季度末具体买了哪些股票，也没有新闻和公告语义。这不是同步遗漏，而是当前授权边界。免费预测 V1 必须把这一限制直接展示给用户，并用下一份设计文档中的回测结果证明它在已有数据下到底能做到什么程度。
