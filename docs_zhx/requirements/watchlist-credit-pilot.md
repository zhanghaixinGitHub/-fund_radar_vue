> 变更等级：L2（用户权益、管理员操作和权限/审计链路）

## 1. 目标

在实际支付、充值或订阅功能之前，验证“按有效关注基金数量提供持续跟踪能力”的产品模型。

所有注册用户可免费浏览基金市场，并默认拥有 5 个有效关注名额。系统管理员可向指定用户发放“试用关注积分”；积分只用于临时扩容有效关注名额，不具有货币、投资、交易或数据所有权属性。

本功能不决定“关注后详情”具体展示哪些字段。净值历史、事件、提醒和后续分析能力的解锁范围，待对应产品需求另行确认。

## 2. 已确认的范围

### 2.1 注册后免费浏览

- 用户完成注册并登录后，可免费浏览基金市场的基础信息。
- 基金市场的数据同步范围继续由已授权且启用的市场基金份额决定，不得因用户是否关注、积分多少或管理员发放情况而缩小或扩大。
- 基础信息与后续深度信息的最终字段边界，待“关注后详情”专题确认；本需求不提前限制现有详情字段。

### 2.2 免费有效关注额度

- 每个启用的基金用户默认拥有 5 个免费有效关注名额。
- “有效关注”是用户当前处于关注状态的基金份额；同一用户重复关注同一基金只能保留一条记录，不能重复占用名额。
- 用户取消关注后，该基金不再占用免费额度或试用积分占用额。

### 2.3 试用关注积分

- 名称统一为“试用关注积分”，不得称为余额、现金、币、储值或投资本金。
- 1 个试用关注积分可同时扩容 1 个有效关注名额。
- 当用户的有效关注数超过免费额度 5 时，每增加 1 个有效关注，锁定 1 个可用试用关注积分；取消该额外关注后，锁定的积分自动释放为可用积分。
- 积分不可充值、购买、转赠、提现、兑换现金或兑换任何交易/投资建议；本阶段没有价格、人民币换算、支付订单、发票或会员订阅。
- v0.1 默认不设置过期时间。若将来需要过期、撤销或套餐到期，必须先定义已锁定积分的保护与用户通知规则，再实施。

### 2.4 管理员发放

- 仅 `SYSTEM_ADMIN` 可向指定的启用用户发放或在受控条件下调整试用关注积分；普通基金用户和数据运营角色无此权限。
- 每次管理员操作必须记录操作人、目标用户、变动数量、变动前后状态、业务原因、时间和 TraceID/Audit ID；不得记录完整手机号、密码、Cookie、CSRF 值或其他敏感认证信息。
- 管理员不得直接覆盖用户的“当前余额”数值。积分状态必须由可追溯的发放、锁定、释放和必要人工调整流水推导。

### 2.5 存量关注平滑迁移

- 启用本功能前已存在的用户关注记录必须全部保留；不得为了满足新的免费额度而自动取消、删除、暂停或迁移任何既有关注。
- 对启用时有效关注数大于 5 的每名既有用户，系统一次性发放 `max(当前有效关注数 - 5, 0)` 个“存量关注迁移积分”，并立即锁定到其超出免费额度的既有关注上。
- 迁移后，既有用户的全部关注继续有效；其可用积分可能为 0，但其已锁定积分足以覆盖当前的额外关注。用户取消其中任一额外关注时，对应积分按通常规则释放，可用于新增其他关注。
- 迁移任务必须按用户幂等执行并有明确迁移标识；重复执行不得重复发放积分、重复锁定积分或改变既有关注记录。
- 具体账户只通过内部稳定用户标识定位。需求、审计展示和日志不得写入用户姓名、完整手机号或其他非必要个人信息。

## 3. 核心口径

| 术语 | 定义 |
| --- | --- |
| 免费有效关注额度 | 每个用户固定拥有的 5 个并发有效关注名额，不是积分账户余额。 |
| 可用试用关注积分 | 已由管理员发放、尚未被额外有效关注锁定的积分数量。 |
| 锁定试用关注积分 | 与某一额外有效关注一一对应、暂时不可用于其他关注的积分。 |
| 有效关注上限 | `5 + 可锁定的试用关注积分总数`；具体一次操作是否可创建关注，仍以服务端实时状态为准。 |
| 关注取消 | 删除当前用户的关注关系；若该关系锁定积分，则同一事务释放对应积分。 |
| 存量关注迁移积分 | 启用额度功能时，按既有有效关注数超出 5 的部分一次性发放并立即锁定的试用关注积分；只用于保护历史关注，不删除历史数据。 |

示例：用户获发 3 个试用关注积分后，最多可同时有效关注 8 只基金。已关注第 6、7、8 只时，3 个积分均处于锁定状态；取消第 7 只后，可用积分恢复为 1，当前有效关注数为 7。

## 4. 业务流程大纲

1. 用户注册、登录后免费浏览基金市场，并可在未超过可用名额时关注基金。
2. 前 5 个有效关注只占用免费额度；第 6 个及以后关注需要服务端锁定 1 个可用试用关注积分。
3. 积分不足时，服务端拒绝创建该关注关系，并返回明确、非投资导向的“有效关注名额已用完”提示；前端不得自行推断或绕过额度。
4. 用户取消额外关注时，服务端在同一事务内删除/停用关注关系并释放该基金对应的锁定积分；重复取消保持幂等，不重复释放积分。
5. 系统管理员在后台选择目标用户、填写正数积分和业务原因后发放积分；成功后用户可用名额增加。
6. 功能首次启用前，对所有存量用户先执行幂等迁移：保留现有关注，按超出免费额度的数量发放并锁定迁移积分；迁移完成后才启用新增关注的额度校验。
7. 用户与管理员均只能看到其职责所需的状态：用户查看本人免费额度、已关注数、可用/锁定积分；管理员可审计授权范围内的发放、迁移与调整记录。

## 5. 非范围与硬边界

- 不接入支付渠道、银行卡、微信、支付宝、应用商店内购、充值、退款、发票或真实订阅。
- 不引入基金申购、赎回、自动交易、收益保证、具体买卖指令或以积分兑换投资建议。
- 不改变已授权数据源、市场同步任务、数据授权范围、数据保留期限或基础市场数据的公开/展示许可。
- 不在浏览器保存或信任积分余额、额度判定结果、管理员身份或其他授权结果；所有写入和限额判定以 Java 服务端认证上下文为准。
- 不因试用积分状态而删除用户既有基金关注或隐藏其基础市场信息。
- 不在需求、页面、日志或审计展示中写入用于迁移定位的用户姓名或完整手机号；管理员操作以内部用户标识和脱敏展示信息完成。
- 本需求不规定“关注后详情”的字段、模型评分、提醒种类或收费价格。

## 6. L2 风险与实施原则

我按七维检查，仅以下 3 项存在真实风险：

1. 权限与审计：管理员发放属于用户权益变动，必须由服务端从认证会话识别 `SYSTEM_ADMIN`，采用 CSRF/Origin 保护、细粒度审计和原因必填；不能只靠前端隐藏入口。
2. 并发与一致性：同一用户并发关注、取消或管理员调整时，积分锁定/释放与关注记录必须处于同一事务或具备等价的一致性保证；必须有唯一约束和幂等键，防止超额关注、重复释放或负积分。
3. 商业演进与合规：试用积分不应伪装成现金或金融产品。未来接入真实支付、到期套餐、数据商业展示或个性化投资建议前，必须升级为 L3 评审，分别确认支付、数据授权和投资咨询边界。

其余维度按现有 Vue → Java → FastAPI 分层、用户数据隔离、Redis 共享读模型不含用户态、日志脱敏和非交易原则执行。
