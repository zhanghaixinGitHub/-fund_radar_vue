# 基金列表合并评级后的延迟排查（2026-10-16）

## 已确认原因

列表合并评级后，Java 依次读取基金基础资料、保存基础资料缓存、读取评级，再向浏览器返回整页。原来的评级等待因此变成整张列表的等待；此前交付只验证了结果，没有验证响应时间，未发现这个性能问题。

本机 Python 8000 当时由 PyCharm 调试器启动，同时一键同步正在执行基金资料任务。只读 HTTP 采样中，127.0.0.1 的基金列表为 44～242 毫秒，评级为 4.61～4.76 秒；localhost 的两次评级为 1.98 和 6.79 秒。Java 日志中存在评级读取超时。请求没有重新评分，耗时在已发布评级的读取与核验路径。

原读取按基金行联表获取批次完整 JSON，同批多只基金会重复传输和解析同一快照；随后按类别逐一查询成员、结果、证据和方法。首页 10 只基金的一次读取共执行 30 条数据库语句，列表还加载了不展示的完整八维正文。原件路径和内容也会逐件核验。

## 修复与保留边界

- 先定位当前已发布批次，每个完整输入快照只读取一次。
- 在同一次只读事务中批量加载完整批次成员、必要结果字段、来源证据与方法资格；首页数据库语句数由 30 降至 8。
- 列表延迟加载八维正文，详情仍读取正文；逐批输入哈希、成员完整性、八维与等级映射、来源撤回、规则资格、原件内容哈希和有效期检查全部保留。没有跨请求缓存校验结论。
- 原件根目录每包解析一次，原件路径范围、大小和哈希仍逐件检查。
- 基金与评级仍由列表同次返回，前端不恢复独立评级请求，也不再显示“评级读取中”。
